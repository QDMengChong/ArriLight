# ArriLight 全局设备状态与操作调度设计提案

设计日期：2026-10-08。本方案优先让设备具备发送翻转命令的条件，再补齐设备资料。每台设备的状态、初始化进度和操作队列由应用全局管理，页面只观察状态并提交操作。

已确定：默认同时推进 5 台设备，允许设置为 1～5 台；超过并发上限的设备排队。2026-10-08 已完成第一版实现，实施顺序见 [实施路径](DeviceRuntime-Implementation-Plan.md)，代码落点、测试结果及真机验证范围见 [实施结果](DeviceRuntime-Implementation-Results.md)。以下内容保留设计依据；实际期限、重试与平台边界以结果文档为准。

## 全局状态集合

按规范化设备地址保存唯一的运行记录。设备连接、认证、通知、资料读取和待执行命令均归属于该记录，主页、控制页、设备信息页及日程页读取同一份状态。

每条记录包含三个部分：

| 部分 | 记录内容 | 用途 |
| --- | --- | --- |
| 会话状态 | 应用是否前台、连接阶段、连接代次、响应通道、认证结果、当前操作限制 | 判断现在能否发送翻转 |
| 资料状态 | 每项资料的值、来源、更新时间、所属连接代次、读取结果和待更新标记 | 判断哪些资料可信、哪些还需补齐 |
| 调度状态 | 当前步骤、已完成步骤、待执行步骤、用户命令、重试期限与错误原因 | 决定下一步，并支持暂停后继续 |

有序集合表示各步骤具有前置依赖和默认执行顺序。一次连接完成的认证在断开后必须失效；历史灯状态可以保留用于展示，但不能让设备继续显示在线。因此应同时保存步骤进度和当前有效条件，不能只保存一个一直递增的阶段编号。

每个步骤使用“待执行、执行中、成功、不适用、失败、已失效”等结果。任务失败和任务被暂停分开记录，资料查询失败不能直接清空已成功建立的认证会话。

同一设备的状态由一个负责者顺序更新，统一发布带有递增快照版本的结果。所有页面按地址读取最新快照，显示较慢的页面回调不能覆盖较新的结果；页面自己的草稿、动画和输入焦点不进入设备运行状态。

## 离线 在线 就绪的含义

| 列表状态 | 判定条件 | 用户点击翻转后的行为 |
| --- | --- | --- |
| 离线 | 发送翻转的必要条件尚不成立，可能未连接、正在连接、待认证或认证失败 | 提交请求，优先完成该设备的必要步骤；超时或无法认证时返回明确结果 |
| 在线 | 当前连接的必要 GATT 通道和认证已完成，应用允许发送命令，具备 OnOff 能力 | 优先发送翻转，无需等待灯状态或完整资料 |
| 就绪 | 在线，并且该设备本轮所需资料全部完成，相关通知通道已建立 | 与在线一样可以翻转，其他控制界面也具有完整资料 |

“在线”按控制能力定义，不以原生 BLE 的 Connected 事件单独判定。内部仍保留“已连接但待认证”的阶段；列表可在“离线”旁显示连接中、认证中、待重试等说明，不新增第四种主状态。

“就绪”包含“在线”。按钮正在执行命令时显示忙碌并阻止重复点击，不必把在线改成离线。用户操作使某项必需资料失效时，可从就绪降为在线，补齐后重新就绪。物理锁定、固件升级等限制用原因和操作可用性表达。

在线表示能够发送有协议响应的翻转请求，硬件仍可能返回锁定或其他业务拒绝；收到明确拒绝后应更新限制原因。不能把发送条件成立当作业务必定成功。

## 每台设备的更新顺序

默认顺序如下。收到用户操作后允许在步骤边界调整顺序，但必须满足该操作的前置依赖。

设备能力已经保存在本地，加载设备记录时即可根据 OnOff 判断是否支持开关控制、根据 SecureControl 确定是否需要认证，并根据灯效、颜色、时钟等能力确定后续资料清单。这些都是本地处理，不增加 BLE 通信，也不作为独立更新阶段。

| 顺序 | 更新步骤 | 是否为发送翻转的前置条件 | 完成后的状态 |
| --- | --- | --- | --- |
| 0 | 加载本地地址、名称、Token、已保存能力及历史资料，建立运行记录，并确定认证要求与资料清单 | 本地记录是连接与认证的输入 | 离线，等待调度 |
| 1 | 按保存的 MAC 或 UUID 直接连接设备 | 是 | 离线，正在准备 |
| 2 | 找到 AGP 服务和必要特征，确认 Control Point 支持写入及 Indicate，建立响应订阅和客户端 | 是 | 离线，正在准备 |
| 3 | 按本地 SecureControl 能力使用已保存 Token 认证；无此要求的设备将认证步骤记为不适用 | 是 | 立即发布在线 |
| 4 | 检查用户命令队列；存在翻转请求则先发送并处理协议响应 | 有请求时优先执行 | 在线 |
| 5 | 建立 Light State Notify，取得本次连接的灯状态；有效通知已提供当前资料时可省去重复读取 | 否 | 在线，已知开关与亮度等 |
| 6 | 读取当前灯效配置，再读取本机触摸模式；仅执行本地能力记录声明支持的操作 | 否 | 在线 |
| 7 | 读取相对延时开灯与关灯配置；仅在 RelativeTimer 支持时执行 | 否 | 在线 |
| 8 | 按颜色能力建立 Color State Notify 并读取颜色状态；CTL 设备补齐范围 | 否 | 在线 |
| 9 | RTC 设备读取时间状态并按既定策略校时；Scheduler 设备读取日程清单与槽位 | 否；依赖时钟的用户命令另行要求时钟条件 | 在线 |
| 10 | 读取固件版本、硬件版本等设备信息，并完成需要的缓存校验 | 否 | 在线 |
| 11 | 检查所有适用资料步骤，发布本轮完整快照 | 否 | 就绪 |

核心路径是：**加载本地记录（地址、Token、能力）→ 直接连接 → AGP 响应通道 → 按需认证 → 在线 → 优先处理翻转 → 补齐资料 → 就绪**。

本地能力只有缺失或明确失效时才补读 Capabilities，例如旧记录没有能力信息，或固件升级后已将能力记录标为失效。补读属于异常恢复分支：在连接和响应通道准备后、需要依据能力执行认证前完成，并更新本地记录。正常启动、重连及页面跳转均不重复读取设备能力，也不将能力重读列为就绪条件。

Token 可以持久化，但认证结果属于当前连接。新连接仍需按本地 SecureControl 要求重新认证，不能因为 Token 和能力已保存在本地而复用上一条连接的认证结果。

Light State Notify 排在在线之后，因为发送翻转只依赖 Control Point 响应通道，不依赖已有灯状态。若翻转发生时该状态订阅尚未建立，先发送命令，随后优先建立结果订阅，并按协议的完成通知或后续读取确认结果；不能把这一阶段的订阅省略理解为无需处理翻转结果。

当前 PW01 不声明 RTC、Scheduler 和颜色模型等能力，相应步骤应直接记为不适用。不可向所有设备无条件发送整套查询。新增能力必须同时定义读取方式和资料有效性，不能仅凭能力位假设客户端已经支持读取。

设备的版本和能力缓存可以缩短首次可操作的路径，但当前能力位及版本号不能独立区分旧固件是否支持 ONOFF_SET=2。此方案以已经支持翻转的 PW01 为目标；不能通过发送一次翻转来探测能力。实际操作若返回不支持或参数无效，应记录兼容性原因，不自动改发基于历史状态推断的 ON/OFF。

## 就绪所要求的资料范围

“所有信息”限定为当前产品和客户端支持的 BLE 资料清单，包含基础灯状态、已支持的灯效、本机模式、相对延时、颜色、时钟、日程和设备信息。云端固件更新列表、手机本地预设和分享内容不属于设备初始化的远程资料。

动态资料需要属于当前有效连接或经过明确验证；静态资料可按设备身份及版本的有效期策略使用缓存。本轮资料验证计划仍需完成，不能因为界面能显示旧值就宣告就绪。旧值保留时标明它是历史缓存。

设备明确不支持某项功能，或者标准可选特征确认不存在，属于“已确定不适用”，不会阻止就绪。已声明支持但读取失败的资料仍待补齐，设备保留在线并显示资料未完整；默认值和吞掉的异常不能替代读取成功。

分步读取取得的是各项资料的最新已知值，不承诺所有值来自硬件同一瞬间。通知和读取回写时检查连接代次及对应资料的版本，防止迟到读取覆盖较新的通知；不同资料的版本不相互比较。

## 设备之间的更新顺序与并发

启动时先建立全部已保存设备的本地记录，不等待网络或完整页面绘制，再开始初始化。演示设备不占用真实 BLE 初始化名额。

初始化队列先处理用户正在操作的目标，再按置顶、最近操作时间、加入时间及地址依次确定顺序。主页选择按名字显示时，不必改变设备准备顺序；显示排序与初始化优先级分别管理。

并发配置控制同时推进初始化的设备数量，默认 5，上下限 1～5。设备少于上限时全部开始，超过上限时排队。以 8 台设备为例，第一批最多 5 台开始准备；某台完成关键准备、结束一个可调度步骤或失败退避后，调度器允许后续设备推进。

跨设备优先完成“可翻转”阶段，再使用空闲资源补齐资料。已经在线的 A 设备不应连续读取全部日程槽位，让尚未开始连接的 B 设备长期等待。某台设备连接慢或离线也不能让另外几台等待它的完整初始化。

每台设备同一时刻只执行一个 GATT 操作或 AGP 请求，同一连接只保留一个未完成 AGP 请求。不同设备可并行推进，原生适配器的必要串行点按平台协调。不能把某台设备连接、认证和全部查询的等待时间一并放进跨设备的大锁。

并发初始化数量与同时保持连接的数量是两个配置概念。五台初始化完成后若仍保持连接，准备第六台可能需要第六条连接。第一版可对实际设备数量较少的场景保持前台会话；设备数量较多时应增加可配置的连接预算，先释放没有用户请求的低优先级会话，再准备目标，释放时同步降为离线。

默认五台是调度目标，Android 与 iOS 是否能稳定同时建连、是否需限制原生建连并发，应通过真机数据确定；允许将初始化并发下调到 1～4，不能把平台真实并发能力当作已验证事实。

## 翻转请求的插入与打断规则

建议优先级为：生命周期停止与设备删除等强制事件 → 用户命令、它缺少的前置步骤及必要结果同步 → 其他设备的关键准备 → 普通资料补齐与重试。已发送命令的协议响应始终必须处理，不能因为队列优先级改变就遗弃响应。

| 点击时正在做的事情 | 处理方式 | 保留内容 |
| --- | --- | --- |
| 目标设备尚未开始连接 | 将目标的必要准备提升到队列前部，翻转等到在线再发送 | 已有设备记录及准备计划 |
| 目标正在连接、建立响应订阅或认证 | 继续完成这些前置步骤，不取消或重来 | 已完成前缀、连接与认证进度 |
| 目标已在线，普通查询还未发送 | 暂停或后移这些查询，先发送翻转 | 连接、认证、已取得资料 |
| 目标已在线，普通查询已经发送 | 默认等当前请求或原生读取结束，在下一个步骤之前插入翻转 | 会话及当前请求的合法结果 |
| 目标正在读取多个日程槽位 | 当前槽位结束后插入；剩余槽位继续留在队列 | 已读取槽位和后续进度 |
| 查询超时或连接损坏 | 按真实会话有效性更新状态，必要时重连认证，再处理仍有效且未发送的用户请求 | 历史资料；失效会话条件不保留 |

打断的主要对象是“后续步骤的调度”，不是销毁设备状态，也不是一律取消正在执行的原生请求。只有底层明确支持取消且不会破坏响应匹配与连接时，才可以取消在途只读任务；第一版采用步骤边界插入更易验证。

例一：点击时处于认证中，顺序变为“完成认证 → 在线 → 翻转 → 结果同步 → 状态及其他查询”。

例二：点击时已经在读取灯状态，顺序变为“完成当前读取 → 翻转 → 取得翻转后的结果 → 继续其他查询”。取消读取若会触发现有代码的客户端释放，就不能用它实现快速插入。

操作的前置依赖按类型定义。翻转依赖可发送命令的条件；颜色设置另需对应能力与范围；带一次性延时的翻转在命令之后还需确认实际结果；日程设置另需有效时钟。不能把“等待就绪”作为所有用户操作共同的前置条件。

## 翻转结果和资料回写

每个用户请求保存唯一操作标识、创建时间、目标、截止时间和执行阶段。至少区分“等待前置条件、待发送、已发送、已接受、已确认、明确失败、结果未知、已取消”。

翻转是非幂等命令。进入队列并不等于已发送，协议接受也不等于硬件已完成。超时、断连或应用进入后台后，已发送但未收到结果的请求记为结果未知，不自动再次发送；新窗口也不能恢复执行旧的翻转请求。

应用进入后台或关闭时，尚未发送的翻转意图取消并同步结果。恢复到前台后需要用户重新点击，避免离线期间的旧意图在很久以后突然执行。页面跳转本身不撤销已经提交的意图，应用停止则结束它的有效期。

PW01 保留 ONOFF_SET=2 的立即接受响应及渐变完成后的状态通知。命令接受后优先进行结果同步；通知缺失时读取一次确认。读取失败保留未知结果，不凭点击前的缓存猜测已经开灯或关灯。

Busy 明确表示本次未执行时，可以依据协议规则有限重试；该规则不能扩大为对所有超时进行重试。也不要把两次翻转合并成无操作，或者只保留最后一次，除非产品明确改变用户点击的含义。第一版继续限制同一设备同时只有一个正在处理的翻转意图。

若用户启用一次性延时关灯，翻转后确认为开启再设置 DELAY_OFF_SET；确认为关闭则不设置，结果未知则保留提示。这个后续步骤属于该用户操作，优先于普通资料补齐。

翻转后，之前排队或在途的灯状态查询结果需要检查是否已过期。旧读取可以完成，但不能在新的确认状态之后覆盖界面。保留连接代次、状态版本和本地操作顺序，并在不确定时安排一次新读取。

## 页面与应用生命周期

| 事件 | 全局状态和队列的变化 |
| --- | --- |
| 页面跳转 | 只变更页面订阅及关注度；连接、认证、初始化和已提交用户命令继续由全局集合管理 |
| 进入控制页或设备信息页 | 立即展示已有快照，将该页面所需缺失资料提升优先级；不重新启动同一设备初始化 |
| 页面离开 | 取消动画、草稿读取等待等页面工作；页面等待的取消不取消共享初始化，也不默认撤回已提交命令 |
| 应用进入后台 | 先禁止新命令与新初始化，所有记录立即判为不可操作并记录后台原因，再停止扫描、取消任务及释放会话 |
| 回到前台 | 新建运行周期，按并发预算重新建立或验证连接与认证；旧动态资料标为待刷新，重新走在线和就绪路径 |
| 窗口关闭 | 标记关闭，停止队列并清理会话；不保留待恢复执行的翻转意图 |
| 冷启动或同一进程重新开窗 | 从本地记录重建当前有效条件，历史资料可展示，但在线、认证和就绪不能从持久化结果直接恢复 |
| 异常断开或蓝牙关闭 | 相关连接条件立即失效；所有页面观察到同一离线状态，后续按恢复策略重新准备 |
| 设备删除 | 停止该设备调度并使迟到回调失效；完成原生释放后再清理记录，失败时保留可重试的删除状态 |
| 固件升级 | 目标进入独占操作阶段，暂停普通初始化和灯控；完成后使旧资料与会话失效，再重新连接、认证和补齐 |

后台事件不能仅更新已经连上的设备：仍在排队、连接中和认证中的设备也属于这次停止范围。立即失效操作条件与随后完成物理断开是两个步骤，断开清理失败也不能让列表继续显示可以操作。

应用周期和设备连接代次用于过滤旧任务与回调。快速后台恢复或退出重开时，旧周期的认证、读取及清理结果不能把新周期覆盖成在线，也不能迟到关闭刚恢复的连接。

共享状态在进程存活期间保持全局一致。操作系统终止进程后无法继续维持内存状态，重启依据本地记录重建；历史数据、排序选择和上次成功操作时间可以持久化，当前连接及认证只存在于运行时。

## 重试与持续更新

连接、认证和资料查询都需要独立期限，用户等待也需要整体期限。超时释放初始化名额，让其他设备继续；界面显示等待原因，并允许用户主动重试。不能让一个请求无限等待“迟早在线”。

前台初始化的连接重试采用有上限的退避，用户点击可提升目标并提前安排一次准备尝试。Token 缺失或被拒绝时进入需要重新绑定的原因状态，不能在启动时自动发 AUTH_GET_TOKEN 或无限重试。

在线以后优先依赖通知更新动态资料，资料查询失败只重试失败或失效项目。页面进入、手动刷新、能力改变和通知丢失可以触发必要更新。避免每次切换页面都重读全部信息，也避免在前台持续高频轮询全部设备。

此方案继续遵守扫描仅由添加设备页持有的约束。启动初始化、离线重试和前台恢复使用保存地址直连。添加页开始扫描和绑定时协调原生适配器资源，已就绪的其他设备状态不因切换页面而被重置；新绑定设备加入同一运行集合。

初始化读取和后台重试不更新 LastOperatedAt。设备接受用户控制后才记录操作时间，避免自动启动任务改变用户的设备使用顺序。

## 与现有实现的主要差异

本节描述改造前的实现，用于说明规划原因；全局队列、分步订阅和应用生命周期接入已在第一版完成。

目前 AgpLightControlService 已按地址维护客户端和设备状态缓存，BluetoothConnectionService 已按地址保存会话与连接代次，可以作为全局集合的基础。

当前 AgpLightControlService 的业务锁覆盖连接、认证和整个控制资料读取流程，BluetoothConnectionService 也通过共享锁调度原生操作。仅启动五个任务仍会在这些锁上排队；实现并行准备需要按设备分配业务队列，并核对原生共享锁的安全粒度。

当前 GetOrCreateClientAsync 默认建立状态订阅，按需读取能力、认证，再读取灯状态和校时。GetControlProfileAsync 随后读取颜色、CTL 范围、灯效及版本等；控制页离开还会取消部分初始化工作。新方案应拆出“必要准备”和独立的资料步骤，并将共享任务生命周期从页面移至应用。

当前部分资料读取失败会使用默认值继续生成 Profile，不能直接用 Profile 获取成功表示新定义的就绪。当前 WithClientAsync 对操作异常会释放客户端，也不能直接用于无损取消低优先级读取；需要分别处理业务拒绝、只读失败、调度暂停和真正的会话失效。

AgpGattTransport 当前 StartAsync 完成后直接复用，不提供从仅响应订阅升级为完整状态订阅的独立流程。按本提案延后状态订阅时，需要补充可重复安全执行的订阅步骤，并让非必要颜色通道的问题只影响相关资料完整性。

## 后续实现的验收场景

1. 冷启动保存五台设备，最多五台同时推进；认证成功即在线，不等灯状态读取。
2. 保存八台设备，一台连接超时不阻塞其余设备；后续设备能得到初始化机会。
3. 连接中或认证中点击翻转，必要准备只执行一次，命令在在线后恰好发送一次。
4. 有未开始的普通查询时点击翻转，命令先执行，后续查询仍可继续。
5. 正在读取灯状态或日程槽位时点击翻转，当前步骤完成后插入，保留认证会话。
6. 查询返回业务失败时保留在线；必需资料未完整时不显示就绪。
7. 任意页面之间跳转，共享步骤继续，所有页面观察到同一设备快照。
8. 排队、连接中、认证中、在线及就绪的设备均正确处理后台和关闭事件。
9. 快速后台恢复、窗口重开、设备删除后，旧回调不能复活失效会话或覆盖新资料。
10. 翻转已发送但超时或断连，记录未知结果；恢复时只查询状态，不自动重放命令。
11. 翻转结果为开启才设置延时关灯，状态未知时不猜测方向。
12. 无 RTC、Scheduler、颜色或 LocalMode 的设备跳过对应步骤；资料未声明支持时不盲目查询。
13. 开关、控制页、启动初始化和重试均不会启动扫描；只有添加设备页启动扫描。
14. Android 与 iOS 分别测量从启动到首台在线、五台在线、全部就绪的时间及失败率，据此确定原生连接与 GATT 调度的实际并发限制。
15. 本地能力有效时，冷启动、重连和页面跳转均不发送 Capabilities 读取；认证要求和资料清单直接使用本地记录。
16. 本地能力缺失或明确失效时，仅目标设备进入补读分支，补读成功后保存结果并继续准备，不阻塞其他设备。
